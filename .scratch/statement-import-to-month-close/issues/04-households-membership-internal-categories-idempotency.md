# 04: Households, membership, Internal Categories and Idempotency-Key

**What to build:** a User creates a Household with a name and a Base currency, becomes its member, and can list and open their Households. Each new Household comes with its three Internal Categories (Opening balance, Household transfer, Uncategorised). A User who isn't a member gets 404 for that Household and anything under it. Every POST endpoint, now and later, honours `Idempotency-Key`. Spec: `../spec.md` stories 3–8, 43, 52, 72, "Request transaction", "Authorisation"; ADR-0003, ADR-0014.

**Blocked by:** 03 (Bootstrap and registration)

**Status:** claimed

- [ ] Household Decider with membership in its fold; `POST/GET /households` and `GET /households/{household_id}`
- [ ] Creating a Household seeds its three Internal Categories in the same database transaction (this ticket introduces the Ledger Category aggregate only as far as seeding needs)
- [ ] Each Household-scoped request opens one database transaction as `wa_app`: it resolves the caller's User in instance scope, then sets `app.household_id` from the path before any Household-scoped query; every repository query also filters by `household_id`
- [ ] Household-scoped routes answer 404 to non-members and to unregistered callers; `/households` answers 403 `registration-required` to unregistered callers
- [ ] POST endpoints accept `Idempotency-Key`: a replay with the same key and body returns the stored response; the same key with a different body gets 422. Later POSTs get this by default
- [ ] A reusable integration test pattern proves row-level security blocks another Household's rows with the query filters bypassed, applied to every Household-scoped table this ticket adds
- [ ] Integration test: a transaction with a Household set can't read or write Users, Invitations or instance-level events, and a transaction in instance scope can't touch Household rows
- [ ] HTTP tests: two Users in two Households; each gets 404 for the other's Household; Idempotency-Key replay and mismatch
- [ ] The consistency map's Create Household row says three Internal Categories, not four, matching the spec

## Comments

Implementation notes (implementer agent):

- **Where things live.** Household Decider in `internal/households/domain/household.go` (events `created`, `memberadded`; membership is in the fold); the service `app.Households` (`Create`, `List`, `Get`, `InHousehold`) in `internal/households/app/households.go`; fold store and lookups in `internal/households/adapters/postgres/households.go`. Ledger Category Decider (only `SeedInternalCategory` and `CategoryCreated`, whose `parentid` and `internalrole` fields are already in the v1 schema for ticket 05) in `internal/ledger/domain/category.go`; `ledgerapp.Categories` in `internal/ledger/app/categories.go`; fold store and reader in `internal/ledger/adapters/postgres`; HTTP adapter in `internal/ledger/adapters/http`. Migrations `000003_households_and_categories` and `000004_idempotency_keys`. `wiring.NewContexts(pool)` builds every service and wires the cross-context ports; Household and Category are registered for rebuild.
- **Request transaction.** `Households.InHousehold(ctx, household, fn)` is the reusable one: one `wa_app` transaction, the caller's User resolved in instance scope, `app.household_id` set from the path, membership checked, `ErrHouseholdNotFound` (404) for non-members, unknown Households and unregistered callers alike. Ledger reaches it through its own `ledgerapp.HouseholdScope` port; later contexts should do the same. `eventstore.Tx` gained `SetActor`, since the actor is known only after resolving the User.
- **Listing a User's Households under RLS.** Instance scope can't see Household rows, so the Household fold also keeps an instance-scoped membership index, `user_households` (IDs only). Its fold store switches the transaction to instance scope to write it and back. `List` reads the index in instance scope, then sets each Household in turn to read it.
- **Internal Categories.** Households seeds them through a port it declares (`app.InternalCategories`), implemented by `ledgerapp.Categories`, in the creating transaction. Each carries an `internal_role` (`opening_balance`, `household_transfer`, `uncategorised`, unique per Household) so later tickets can find e.g. Uncategorised by role. To observe the seed through the HTTP seam this ticket adds `GET /households/{household_id}/categories`: a flat list with `parent_id` and `kind` as `x-extensible-enum` `INCOME|EXPENSE|INTERNAL`. Ticket 05 owns the full tree and may reshape it.
- **Base currency.** `sharedkernel.ParseCurrency` knows the ISO 4217 currencies in circulation plus BTC and ETH, with their decimal places (ADR-0007), ready for ticket 06. The contract checks the shape (`^[A-Z]{3,5}$`, else 400); an unknown code or a blank name gets 422 `/problems/invalid-household`.
- **Idempotency-Key.** An HTTP middleware (`internal/platform/httpapi/idempotency.go`) honours it on every POST, whatever the contract says; `contract_test.go` fails if a POST in `api/openapi.yaml` doesn't declare `#/components/parameters/IdempotencyKey`. Keys are per OIDC identity (stored as a SHA-256 of issuer, subject and key) and reserved in instance scope before the request runs: a concurrent request with the key gets 409 `/problems/idempotency-key-in-use`, so a double click never runs twice. A 2xx response is stored and replayed; another body (method, path, query and body bytes) gets 422 `/problems/idempotency-key-mismatch`; a non-2xx response releases the key so a corrected request can reuse it. A response holding Household data is stored in `idempotency_responses` under that Household's RLS: the Household in the path, or the one a handler names with `httpapi.ResponseBelongsTo` (`createHousehold` does). Known limits: if the process dies between the command's commit and storing the response, the key stays reserved and retries get 409 (never a second run); reserved keys never expire yet. **For ticket 08:** a multipart upload's body includes a random boundary, so a client that rebuilds the form on retry sends different bytes and would get 422; hash the parts instead of the raw body there.
- **RLS test pattern.** `databasetest.AssertHouseholdIsolation` (a Household-scoped table: unfiltered reads see only its own row, writing another Household's row or moving a row is refused, unfiltered UPDATE/DELETE touch only its own row, instance scope sees and writes nothing) and `databasetest.AssertInstanceScopeOnly`. Applied to `households`, `household_members`, `categories`, `idempotency_responses`, and to the instance tables `user_households` and `idempotency_keys`. Users, Invitations and instance-level events were already covered by ticket 02's and 03's tests in `migrations_integration_test.go`. Mutation checks done by hand: dropping the categories policy fails its RLS test; skipping the membership check fails the two-Households 404 test.
- **Consistency map.** The Create Household row now says three Internal Categories and mentions the membership index row.
