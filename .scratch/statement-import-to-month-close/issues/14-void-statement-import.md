# 14: Void Statement import

**What to build:** a User who imported a file with a wrong mapping voids the Account's latest Statement import, fixes the mapping and uploads the same file again. Voiding the first import also removes the Opening balance, so a corrected first file works it out again. Spec: `../spec.md` stories 43d–43f, 60, "Ingestion: Statement import: Void"; ADR-0018.

**Blocked by:** 10 (Recategorise, reverse Transactions and Discard pending Imported transactions), 11 (Later imports: Balance check and certain repeats)

**Status:** claimed

- [ ] `POST …/statement-imports/{statement_import_id}/void` emits `voided`
- [ ] Allowed only for the Account's latest non-voided import, and only while none of its rows are Accepted
- [ ] All its Imported transactions become Discarded and its file hash is released
- [ ] Voiding the Account's only import reverses the Opening balance Transaction through a Ledger `app` port in the same database transaction, and the Account goes back to awaiting its first Statement import
- [ ] Decider tests: void rules
- [ ] HTTP tests: void and re-upload with a fixed mapping; voiding the first import reopens the Opening balance and a new preview/confirm works; refusing to void an earlier import; refusing to void one with Accepted rows
- [ ] Consistency map row for Void Statement import matches the code

## Comments

Implementation notes (implementer agent):

- **Path.** `POST /households/{h}/connections/{c}/statement-imports/{statement_import_id}/void` (`voidStatementImport`, no body, 200 `StatementImport`). `StatementImport` gains optional `voided_at`; the list keeps showing voided imports with it. Problems, all 409: `/problems/not-the-latest-statement-import`, `/problems/statement-import-has-accepted-rows` (reverse first), `/problems/statement-import-already-voided`. An unknown import, another Household's, or one reached through a Connection it doesn't belong to: 404.
- **Ingestion.** Statement import Decider: `VoidStatementImport{Latest, AcceptedRows}` → `io.walletaccountant.ingestion.statementimport.voided.v1` (`StatementImportVoided{}`); fold gains `VoidedAt` / `Voided()` (schema version 2) and keeps its `OpeningBalance`, so a voided first import still shows what it had. Imported transaction Decider: `DiscardForVoid` → the existing `ImportedTransactionDiscarded` from any state but Accepted (Accepted refused; already Discarded records nothing), so a kept or Suspected duplicate row from ticket 12 is Discarded by void too. `StatementImports.Void` locks the Account's imports (same advisory lock as later uploads), reads `LatestImport` (greatest non-voided UUIDv7 of the Account, across its Connections) and `RowsOf` the import, runs the Decider, Discards every row (each row re-checks its own state, so an Accept racing the void refuses one or the other), and, when the import has an Opening balance, calls the new Ledger port method `ReverseOpeningBalance` (`internal/wiring/ledgerport.go`).
- **Ledger.** Transaction Decider: `ReverseOpeningBalance{ReversalID}` → the existing `TransactionReversed`, allowed only for the Opening balance Transaction (`ErrNotTheOpeningBalanceTransaction` otherwise), once. Account Decider: `ReopenOpeningBalance{TransactionID, ReversalID, Amount}` → `io.walletaccountant.ledger.account.openingbalancereversed.v1` (refused while awaiting, or for a Transaction that isn't its Opening balance); the fold goes back to awaiting, unlinks the Opening balance Transaction and moves the start month back. `ledgerapp.Transactions.ReverseOpeningBalance` records the reversal with `TransactionState.Reversal` (linked both ways, listed in the Account transaction list). `Transactions.Reverse` still refuses the Opening balance.
- **Migration** `000013_void_statement_imports`: `statement_imports.voided_at`; `statement_imports_file_idx` recreated as a partial unique index `WHERE voided_at IS NULL` (same name, so the fold store's duplicate detection still works); index on `imported_transactions (household_id, statement_import_id)`. No new table, so no new RLS test. `ImportOfFile` and the Balance check's Opening balance sum both skip voided imports (a mutation dropping the latter fails `TestVoidingTheFirstImportReopensTheOpeningBalance`).
- **Tests.** Decider: `internal/ingestion/domain/void_test.go` (void, fold, every refusal; `DiscardForVoid` from pending, from returned-to-pending, already Discarded, Accepted refused), `internal/ledger/domain/void_opening_balance_test.go` (reverse the Opening balance and its refusals; reopen, balance back, a new Opening balance recorded after; refusals). HTTP `internal/ingestion/adapters/http/void_integration_test.go`: void and re-upload the same file with a fixed mapping (wrong description column), voiding the first import (inverted sign) reopens the Opening balance, then preview/confirm and a later import's check counts only the new one; refusing to void an earlier import (then void the later one, then the earlier one); refusing one with Accepted rows, then reverse and void; already voided; 404s (other Household both ways, other Connection, unknown); Idempotency-Key replay; rebuild.
- **For the merge with ticket 12.** Void Discards every non-Accepted row via `DiscardForVoid`, which accepts any state except Accepted/Discarded, so Suspected duplicate and kept rows are covered without change. If ticket 12 stores a waiting/failed `balance_check`, nothing in void reads it; a voided import with a waiting check presumably shouldn't block Month close (ticket 15 should ignore voided imports). Closed-month flags for a void (ticket 16) aren't set.
