# 12: Suspected duplicates, Keep, and the waiting Balance check

**What to build:** when a later file has rows that only look like earlier ones, they are imported as Suspected duplicates rather than skipped, and each is shown next to the row it resembles. A User Keeps one (it becomes pending) or Discards it. The import's Balance check waits until every Suspected duplicate is decided, then passes or fails. Spec: `../spec.md` stories 39, 40, 40b–40e, 43c, "Ingestion: Imported transaction".

**Blocked by:** 10 (Recategorise, reverse Transactions and Discard pending Imported transactions), 11 (Later imports: Balance check and certain repeats)

**Status:** resolved

- [ ] Suspected duplicate: same bank transaction ID with a different Booking date or amount; or, without a bank transaction ID, same Account, Booking date, amount and normalised description as a row from an earlier import. Never compared within the same file
- [ ] Each Suspected duplicate records the earlier Imported transaction it resembles, and the list (`state=suspected_duplicate`) shows both
- [ ] `POST …/imported-transactions/{imported_transaction_id}/keep` moves a Suspected duplicate to pending; Discard (from ticket 10) also accepts Suspected duplicates
- [ ] An import with Suspected duplicates is recorded with its Balance check waiting; deciding the last one runs it and records `balancecheckpassed` or `balancecheckfailed`
- [ ] The import result reports the Suspected duplicate count
- [ ] Decider tests: Suspected duplicate transitions, waiting check resolving to passed and to failed
- [ ] HTTP tests: overlapping files without bank IDs; same bank ID with a different date or amount; identical rows within one file both imported; Keep; Discard; check waiting then passing; check waiting then failing
- [ ] Consistency map row for Keep or Discard Imported transaction matches the code

## Comments

Implementation notes (implementer agent):

- **Paths and contract.** `POST /households/{h}/imported-transactions/{id}/keep` (`keepImportedTransaction`, 200 `ImportedTransaction`, now `PENDING`), beside ticket 10's `…/discard`, which now also takes Suspected duplicates. Imported transaction `state` (filter and schema) gains `SUSPECTED_DUPLICATE`; `ImportedTransaction.resembles` (new `ResembledImportedTransaction`: id, Statement import, state, Booking date, amount, description, bank ID) shows the earlier row, on every read (list, Keep, Discard, Accept), and stays after the decision. `StatementImport.suspected_duplicates` (required int32; these rows are also counted in `rows_imported`); `balance_check` gains `WAITING` and `FAILED`. Problems: Keep of anything not a Suspected duplicate → 409 `/problems/imported-transaction-not-suspected-duplicate`; Accept of a Suspected duplicate → 409 `/problems/imported-transaction-suspected-duplicate`; unknown / another Household → 404.
- **Matching.** `domain.Statement.WithSuspectedDuplicates([]ImportedKey)` (pure, run after `WithoutCertainRepeats`): a row with a bank ID resembles an earlier row with the same bank ID (date or amount differ, since exact repeats are already gone); a row without one resembles an earlier row with the same Booking date, amount (by value) and `NormaliseDescription` (lower case, white space collapsed and trimmed). Earlier rows are every non-Discarded Imported transaction of the Account (`ImportedKey` gains `ID` and `Description`; `ImportedSoFar` now returns all of them, ordered by Booking date and ID, so the first match is named). A row with a new bank ID is never compared by description. Rows of the same file are never compared.
- **Deciders.** Imported transaction: `ImportRow.Resembles` → `TransactionImported.resembles` (fold state `suspected_duplicate`, `Resembles`); `KeepImportedTransaction` → `…importedtransaction.kept.v1` (only from Suspected duplicate); Discard accepts Suspected duplicates; Accept refuses them (`ErrImportedTransactionSuspectedDuplicate`). Statement import: `RecordStatementImport.SuspectedDuplicates` > 0 on a later import records `balancecheck: waiting` whatever the check would say; `RunBalanceCheck{OpeningBalance, Total}` → `WaitingCheckPassed` (`…statementimport.balancecheckpassed.v1`) or `WaitingCheckFailed{Expected, Difference}` (`…statementimport.balancecheckfailed.v1`), refused unless waiting (`ErrBalanceCheckNotWaiting`). A failed check keeps the import (it is fixed by voiding, ticket 14; Month close, ticket 15, must refuse while `waiting` or `failed`). Fold schema versions: Statement import 2, Imported transaction 3.
- **Running the waiting check.** `ImportedTransactions.Keep`/`Discard` share `decide`: if the row is a Suspected duplicate, the Account's import lock (ticket 11's `LockAccount`) is taken before the decision, then `UndecidedSuspectedDuplicates` of its import is counted and, at zero, `ImportedUpTo` (Opening balance + non-Discarded rows of that import and those recorded before it, by `(recorded_at, id)`) feeds `RunBalanceCheck`, all in one transaction. The check is recomputed at decision time rather than snapshotted at upload, so an earlier row Discarded meanwhile is left out, as the Balance check definition says. A concurrency test decides an import's two last Suspected duplicates at once in four Households; removing the lock makes it fail (checked by hand).
- **For ticket 13 (Notifications).** React to `io.walletaccountant.ingestion.statementimport.recorded.v1` whose data has `suspectedduplicates` > 0 (omitted when 0); the event's subject/stream ID is the Statement import ID, and `accountid`/`connectionid` are in the data.
- **For ticket 14 (void).** `ImportedUpTo` sums `opening_balance` over all the Account's imports, same as `ImportedSoFar`; when 14 leaves a voided first import's Opening balance out of `ImportedSoFar`, do the same in `ImportedUpTo` (both in `internal/ingestion/adapters/postgres/statementimports.go`). Voiding should Discard Suspected duplicates too (they're non-Accepted).
- **Migration** `000012_suspected_duplicates`: `imported_transactions.resembles_imported_transaction_id`, `statement_imports.suspected_duplicates`, and a partial index for counting an import's undecided Suspected duplicates. No new table, so no new RLS test.
- **Tests.** Decider/domain (`internal/ingestion/domain/suspected_test.go`): matching (bank ID with another date/amount, no-ID with normalised description, other description/day, new bank ID, identical rows within the file), Suspected duplicate import and fold, Keep → pending → Accept, Discard, Keep/Accept refusals, waiting import recorded, check running to passed and to failed, run refused unless waiting. HTTP (`suspected_integration_test.go`): overlapping files without bank IDs (counts, `WAITING`, list with `resembles`), same bank ID with another date or amount, identical rows within one file (first and later import), Keep + Discard → check passes, Keep + Discard → check fails, refusals, another Household 404 (both paths), Idempotency-Key replay of Keep, concurrent last decisions, rebuild. Ticket 11's `TestRowsWithoutBankIDsAreNeverCertainRepeats` is replaced by the overlapping-without-IDs test (those rows are now Suspected duplicates, not refused); `TestAWrongMappingIsCaughtByTheBalanceCheck` now refuses a non-overlapping file outright and shows an overlapping one waiting, then failing once the inverted rows are Discarded.
