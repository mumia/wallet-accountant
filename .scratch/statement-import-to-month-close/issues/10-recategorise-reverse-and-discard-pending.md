# 10: Recategorise, reverse Transactions and Discard pending Imported transactions

**What to build:** a User gives an Uncategorised Transaction its Category or changes a wrong one. A mistaken Accept is reversed: a linked reversing Transaction appears in the list beside the original, and the Imported transaction goes back to pending, where it can be Accepted again or Discarded. Spec: `../spec.md` stories 50–51, 51b–51f, "Ledger: Transaction", "Cross-context calls: Reverse Transaction"; ADR-0018.

**Blocked by:** 09 (Accept Imported transactions)

**Status:** resolved

- [ ] `PATCH …/transactions/{transaction_id}` sets the Category of the non-Account side and emits an event; the Uncategorised count updates
- [ ] `POST …/transactions/{transaction_id}/reverse` emits `reversed` and records a reversing Transaction with opposite Postings, the same Booking date and a link to the original; both appear in the Account's list
- [ ] Reversing a Transaction linked to an Imported transaction returns it to pending through an Ingestion `app` port in the same database transaction
- [ ] Refused: reversing the Opening balance Transaction, a reversal, or a Transaction already reversed; recategorising a reversed Transaction or a reversal
- [ ] A reversed Transaction and its reversal don't count toward the Uncategorised count
- [ ] `POST …/imported-transactions/{imported_transaction_id}/discard` Discards a pending Imported transaction; Discarded is final
- [ ] Decider tests: reversal rules, recategorisation rules, pending → Discarded
- [ ] HTTP tests: recategorise, reverse then re-Accept, reverse then Discard, each refusal; another Household gets 404
- [ ] Consistency map rows for Set Transaction Category, Reverse Transaction and Discard match the code

## Comments

Implementation notes (implementer agent):

- **Paths.** Under the Household, like tickets 08/09: `PATCH /households/{h}/transactions/{transaction_id}` (`changeTransaction`, body `TransactionChange {category_id}` required, 200 `Transaction`), `POST /households/{h}/transactions/{transaction_id}/reverse` (`reverseTransaction`, no body, 201 with the reversing `Transaction`), `POST /households/{h}/imported-transactions/{id}/discard` (`discardImportedTransaction`, 200 `ImportedTransaction`, now `DISCARDED`). New `Transaction` schema: the Transaction from its Account (account, signed amount, dates, description, payee, Category, `imported_transaction_id`, `reversal_of_transaction_id`, `reversed_by_transaction_id`). `AccountTransaction` list items gain the two optional reversal links. `state` (filter and schema) gains `DISCARDED`.
- **Problem types.** Reverse: 409 `/problems/transaction-already-reversed`; 422 `/problems/transaction-is-a-reversal`, `/problems/opening-balance-transaction`. Recategorise: 409 `/problems/transaction-reversed`; 422 `/problems/transaction-is-a-reversal`, `/problems/opening-balance-transaction` (recategorising the Opening balance Transaction is refused too: it is fixed only by voiding), and Accept's `/problems/internal-category` / `/problems/invalid-category` (Uncategorised is allowed, so a Category can be moved back). Discard: 409 `/problems/imported-transaction-already-discarded`, 409 `/problems/imported-transaction-already-accepted` (reverse first). Accept of a Discarded row: 409 `/problems/imported-transaction-discarded`. Unknown or another Household's Transaction / Imported transaction: 404.
- **Shape.** Ledger Transaction Decider: `ReverseTransaction{ReversalID}` → `…ledger.transaction.reversed.v1`; `SetTransactionCategory{CategoryID}` → `…ledger.transaction.categoryset.v1` (with `PreviousCategoryID`; the same Category records nothing); `RecordTransaction`/`TransactionRecorded` gain `ReversalOf`; `TransactionState.Reversal(id)` builds the reversing command (opposite Postings, same dates, description and payee, no Imported transaction link); fold gains `ReversalOf`/`ReversedBy` (schema version 3). Account Decider: `BookReversal` → `…ledger.account.reversalbooked.v1` (moves the month back; takes the original out of the Uncategorised count if it was there), `RecategoriseTransaction` → `…ledger.account.transactionrecategorised.v1` (always recorded, with was/is Uncategorised, so ticket 16 can flag closed months from it). Account fold shape unchanged, so no schema bump. `ledgerapp.Transactions.SetCategory` / `Reverse` in `internal/ledger/app/corrections.go`; the Category rules are shared with Accept (`chooseCategory`). Ledger declares an `Ingestion` port (`ReturnToPending`); `internal/wiring/ledgerport.go` adapts `ingestionapp.ImportedTransactions.ReturnToPending` to it (the services reference each other, so `registry.go` fills the Imported transactions service in after the Ledger is built). Ingestion Imported transaction Decider: `ReturnToPending{TransactionID}` → `…importedtransaction.returnedtopending.v1` (only when Accepted by that Transaction; unlinks it), `DiscardImportedTransaction` → `…importedtransaction.discarded.v1`. Stored state `discarded`, matching ticket 11's `state <> 'discarded'`.
- **Migration** `000011_reverse_transactions`: `ledger_transactions.reversal_of_transaction_id`, `reversed_by_transaction_id`. No new table, so no new RLS test.
- **Tests.** Decider (`internal/ledger/domain/reversal_test.go`, `internal/ingestion/domain/discard_test.go`): reversal event and its links, the reversing command's Postings, every reversal and recategorisation refusal, a split Transaction refused, Account balance and Uncategorised count after a reversal and after recategorising both ways, return to pending and its refusals, pending → Discarded, Discard after reversal, Discarded final. HTTP (`internal/ingestion/adapters/http/corrections_integration_test.go`, beside the Accept fixture): recategorise (and back to Uncategorised, same Category is a no-op), reverse then re-Accept (links in the list, balance, pending row unlinked), reverse then Discard, Discard of a pending row, every refusal changing nothing, Idempotency-Key replay of a reverse, another Household 404 for all three (both paths), rebuild, and a Discarded row left out of a later import's Balance check and certain repeats (a mutation of the stored `discarded` value fails it; so does dropping the return-to-pending call for the reverse tests).
- **Not covered at the HTTP seam.** The Uncategorised count still has no read path until ticket 15 (month status), so "the Uncategorised count updates" and "a reversed Transaction and its reversal don't count" are tested at the Account Decider seam only. Closed-month flags (ticket 16) aren't set; the consistency map rows say so. Discard of a Suspected duplicate (and Keep) is ticket 12's; the Decider refuses anything not pending.
- **For ticket 14 (void).** Reversing the Opening balance Transaction is refused here by the Transaction Decider (`ErrOpeningBalanceTransaction`); voiding the first import will need its own path (e.g. a command that is allowed for the Opening balance) rather than `Transactions.Reverse`.
- **Consistency map.** Set Transaction Category, Reverse Transaction and Keep or Discard Imported transaction rows updated to what the code does.
