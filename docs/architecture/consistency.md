# Consistency map

What each command changes immediately (in the same database transaction) and what follows later through domain events. The rule behind it is ADR-0013: immediate if a User would notice a delay or an inconsistency, deferred otherwise.

Every spec that adds or changes a command adds or updates its row here. Code review checks the code against this table.

| Command | Context | Immediate (same transaction) | Deferred (via events) |
|---|---|---|---|
| Issue bootstrap Invitation | Households | Bootstrap Invitation issued, or reissued with a new code if still unredeemed; its code lookup row updated | — |
| Issue Invitation to a Household | Households | Caller's membership checked (404 otherwise); Invitation issued in Household scope as a new stream, never a reissue, with role `user`, the issuing member as actor and an expiry 24 hours after it is issued; its code lookup row (instance scope, naming the Household) saved with it | — |
| Revoke Invitation | Households | Caller's membership checked (404 otherwise); the Invitation must be open in this Household: not redeemed, not revoked, not expired (404 otherwise); `invitation.revoked` recorded with the revoking member as actor, whoever issued it; its fold row marked revoked. The code lookup row stays, and redeeming the code is refused like a wrong code | — |
| Redeem Invitation (`createRegistration`) | Households | Identity checked not yet a User (409 `already-registered`) and code looked up in instance scope (unknown: 422 `invalid-invitation`). A code naming no Household (bootstrap or an operator's): Invitation redeemed (expired, superseded or redeemed: 422 `invalid-invitation`); User registered with the Invitation's role and the trimmed display name (blank: 422 `invalid-user`), and its identity lookup row saved. A code to a Household: User registered with role `user` and the trimmed display name, and its identity lookup row saved; then the Join Household steps below, so the instance-level events come before the Household's (ADR-0017) and any refusal (expired, revoked or redeemed: 422 `invalid-invitation`) rolls back the registration too | — |
| Join Household (`createMembership`, and `createRegistration` with a Household code) | Households | Caller's User resolved (`createRegistration`: registered just before, as above) and code looked up in instance scope (unknown, or naming no Household: 422 `invalid-invitation`; Unregistered: 403); transaction set to the Invitation's Household; member added with the Invitation's ID (refused with 409 `already-a-member` if already a member, which rolls back and leaves the code unused); Invitation redeemed (expired or redeemed: 422 `invalid-invitation`); membership index rows saved | `member_joined` Notification: a Households handler on `household.memberadded` that carries an `invitationid` (creating a Household adds its creator without one, and raises nothing) raises one naming the member, unread for every member, including the new one; deduplicated through the processed-events table |
| Remove member / leave (`removeMember`) | Households | Caller's membership checked (404 otherwise); `household.memberremoved` recorded with the caller as actor, who left when they removed themselves (a User who isn't a member: 404; the only member: 409 `last-member`); the `household_members` row and the `user_households` index row deleted, so the removed User's next request is refused. Their User, their earlier events and the Invitations they issued stay | `member_left` or `member_removed` Notification: a Households handler on `household.memberremoved` raises `member_left` when the event's `actorid` is its `userid`, and otherwise `member_removed`, which also names the remover (the actor); unread for every remaining member; the list reads both names in instance scope, so a removed member keeps theirs; deduplicated through the processed-events table |
| Rename User | Households | The caller's own User found by their identity (instance scope); `user.renamed` recorded with the trimmed display name (refused when blank; nothing recorded for the same name); the User's row and its display name saved | — |
| Create Household | Households → Ledger | Household created; creator added as member, with the User's membership index row; the four Internal Categories (Opening balance, Household transfer, Uncategorised, Account transfer) created. Account transfer is reached only through a Transfer: Accept and Set Category refuse it like any other Internal Category, and there is no migration for existing Households | — |
| Create Category | Ledger | Household's Category tree locked; parent and sibling names read and checked; Category created | — |
| Add Account | Ledger | Account created, awaiting its first Statement import | — |
| Add Account (cash) | Ledger | The two Opening counts checked equal and in the Account currency first (`opening-count-mismatch`; a missing one, another currency or too many decimal places: `invalid-account`); Account created; then, in the same transaction, the Opening balance recorded on the Account from the count and the Opening balance Transaction (Account ↔ Opening balance Internal Category) recorded on the start date with its Account Posting lookup row, so the Account never awaits a Statement import and has a balance at once. A statement Account sent an Opening count is refused (`invalid-account`) (ADR-0018) | — |
| Recount opening | Ledger | Account read (refused as not found outside the Household, `not-a-cash-account` for a statement Account); the two counts checked as when adding; the current Opening balance Transaction's Posting on the Account read as the previous count; the Account Decider refuses once the start date's month is no longer the Open month (`opening-count-locked`), and records nothing for the same count; otherwise the Account records the old Opening balance reversed and the new one recorded, moving its balance by the difference, the old Opening balance Transaction is marked reversed, a reversal with the opposite Postings on the start date is recorded and linked both ways, and a new Opening balance Transaction is recorded on the start date, all three in the Account transaction list (ADR-0018) | — |
| Record cash Transaction | Ledger | Account read (refused as not found outside the Household; `not-a-cash-account` for a statement Account); the amount checked (zero, another currency or too many decimal places: `invalid-transaction`) and the date checked against today in UTC (a later date: `invalid-transaction`); the Category checked as in Accept (none or Uncategorised books to Uncategorised, any other Internal Category refused); the Account Decider books it in its month, which for a cash Account may be the Open month or any later one (a month before it: `month-closed`, naming the Account; before the start date: `invalid-transaction`), moving the balance and the Uncategorised count; the Transaction (Account ↔ Category) recorded with the date as both Booking and Transaction date and no Value date, with its Account Posting lookup row. With `counterpart_account_id` (sent with `category_id` it is `invalid-transfer`, `CATEGORY_AND_TRANSFER`), the Transaction is a Transfer leg instead: the counterpart read and checked (the leg's own Account: `SAME_ACCOUNT`; not the Household's: `UNKNOWN_ACCOUNT`; another currency: `CURRENCY_MISMATCH`, all `invalid-transfer`). A statement Account counterpart: one leg booked and recorded against Account transfer, naming it, In transit until the bank row's Accept Matches it. A cash counterpart (cash ↔ cash): its leg recorded too, with the opposite amount and the same date, description and payee, both booked in Account ID order, so a closed month of either refuses the command (`month-closed`, naming that Account), and the Match confirmed with both legs marked Matched; the answer is this Account's leg, whose `match_id` names the other (ADR-0024) | Category totals, Budget actuals (not for legs) |
| Create Connection | Ingestion ← Ledger | The Account read through the Ledger port (not found outside the Household; a cash Account refused with `invalid-connection`, since it is kept by hand); Connection created with its name checked unique within the Account and its mapping, if any, validated and saved with mapping version 1 | — |
| Save CSV mapping | Ingestion | Connection's mapping validated as a whole and saved with a new mapping version (also when a Connection is created with its mapping) | — |
| Upload Statement import | Ingestion → Ledger | The Account's Statement imports locked first (every upload, so whether it is the first import can't change under it, and imports are recorded one after the other: their record order, never their IDs, says which is the latest); Connection's mapping, the Account (through the Ledger port) and earlier imports of the same file read and checked; Statement import recorded with its Export balance; new Imported transactions recorded as pending or Suspected duplicate; certain repeats skipped; Balance check run, or left waiting for Suspected duplicates. First import only (its `preview_id` recomputed and checked): one pending Imported transaction per row on or after the start date, then through the Ledger port the Account's Opening balance recorded (refused if it already has one), so it stops awaiting its first Statement import and its balance is set, and the Opening balance Transaction recorded on the start date with its Account Posting lookup row (the Account transaction list). Later imports only (no `preview_id`, Export balance given once; one sent while the Account awaits its first import is refused as needing a preview): its Opening balance and every non-Discarded Imported transaction read from Ingestion's own folds, never Ledger Transactions; rows matching an earlier one by bank transaction ID, Booking date and amount skipped and counted; rows that only look like an earlier non-Discarded one (same bank transaction ID with another Booking date or amount; or, without a bank transaction ID, the same Booking date, amount and normalised description), never compared within the file, imported as Suspected duplicates recording the earlier Imported transaction they resemble, and counted on the Statement import; with no Suspected duplicates the Balance check is run on the rest (the Opening balance and the pending, Accepted and kept rows: an earlier waiting import's undecided Suspected duplicates don't count until kept), and a failed check refuses the whole import, recording nothing, otherwise the Statement import is recorded with its check passed and its new rows pending; with Suspected duplicates the Statement import is recorded with its check waiting, whatever the check would say now. Around the Open month (ADR-0024), later imports only: the Account's Open month is read through the Ledger port with its fold row locked `FOR SHARE`, so a Close or Reopen waits for the import; rows booked before the Open month are split off first, before certain repeats and Suspected duplicates are told, and ignored, counted on the Statement import (`rows_ignored_in_closed_months`); rows in a month not open yet are imported as pending as usual, but can't be Accepted or Discarded until it opens. The Balance check formula is unchanged, so a closed month's row the books lack makes it fail: when an immediate check fails, the split-off rows that are neither certain repeats nor lookalikes of an earlier Imported transaction are counted (`rows_in_closed_months_not_in_books`) and their months named as the ones to Reopen; a waiting check that later fails records only its state. A first import never meets a closed month. The Statement import's lookup row keeps the earliest Booking month of the Imported transactions it recorded | Notification to the Household when Suspected duplicates were found: a Households handler on `statementimport.recorded` with `suspectedduplicates` > 0 (which carries the Statement import, its Connection and Account, and its Suspected duplicate count) raises one "suspected duplicates found" Notification linking to the import, unread for every member; deduplicated through the processed-events table |
| Keep or Discard Imported transaction | Ingestion → Ledger | Keep: a Suspected duplicate moved to pending (refused for any other state). Discard: a pending row or a Suspected duplicate moved to Discarded (refused when Accepted or already Discarded; Discarded is final, and later Balance checks, certain-repeat and Suspected-duplicate matching leave it out). Deciding a Suspected duplicate first locks its Account's Statement imports and reads the row again under the lock (a racing Keep or Discard may have decided it: then a Keep is refused, and a Discard of the now pending row is treated as a pending row's). Then, through the Ledger port, the Account's Open month is read with its fold row locked `FOR SHARE`, so a Close or Reopen of the Account waits for this to commit (ADR-0024). A row booked before the Open month is refused (`month-closed`) before its state is checked. Once its state is checked, a pending row booked after the Open month is refused for Discard (`month-not-open-yet`), while a Suspected duplicate there can be kept or Discarded, so its import's waiting check can run and the Open month can close. Then, if none of its Statement import's Suspected duplicates is left and its check is still waiting, the waiting Balance check is run on the Account's Opening balance and its pending, Accepted and kept Imported transactions from that import and the ones recorded before it, and recorded as passed or failed (a failed check keeps the import; it is fixed by voiding) | — |
| Preview first Statement import | Ingestion ← Ledger | Nothing recorded: the Connection's mapping, the Account (through the Ledger port) and earlier imports of the same file are only read | — |
| Void Statement import | Ingestion → Ledger | The Account's Statement imports locked; its latest non-voided import (the one recorded last) and the voided import's rows read; Statement import voided (refused unless it is the Account's latest non-voided import, none of its rows are Accepted, and it isn't already voided); every row not yet Discarded (pending, kept or Suspected duplicate) Discarded, each checking its own state again so a racing Accept, Keep or Discard refuses one or the other, and a waiting Balance check of the voided import never runs; file hash released (a duplicate file is only one of a non-voided import). First import only (it has an Opening balance), through the Ledger port: the Opening balance Transaction marked reversed, a reversing Transaction with the opposite Postings on the start date recorded and linked both ways (both in the Account transaction list), and the Account's balance moved back as it goes back to awaiting its first Statement import; later Balance checks, waiting ones included, leave the voided import's Opening balance out. After the existing refusals, the Account's Open month and start date are read through the Ledger port with its fold row locked `FOR SHARE`, so a Close or Reopen waits for the Void, and an import that touches a closed month is refused (`statement-import-touches-closed-month`, naming the earliest closed month it touches): one whose earliest Booking month of the Imported transactions it recorded, in any state (kept on its lookup row at record time), is before the Open month, or the first import (it has an Opening balance) while the start date's month is before the Open month. Rows it ignored in closed months never count, so voiding never changes a closed month (ADR-0024). Every Statement import read (list, upload, void) works out `void_blocked_by` from the same rules: the Account's latest import, its Accepted rows counted in one grouped query per Connection, and the Open month read without a lock | — |
| Accept imported transaction | Ingestion → Ledger | The row's Booking month checked against the Account's Open month, read through the Ledger port without a lock: one before it is refused (`month-closed`), then one after it (`month-not-open-yet`), before the row's own state (ADR-0024); Imported transaction marked Accepted (refused unless pending) and linked to its Transaction; through the Ledger port the chosen Category read and checked (none, or Uncategorised, books to Uncategorised; any other Internal Category refused), the Account's balance and Uncategorised count for the Booking month updated, and the Ledger Transaction recorded with the row's exact amount, dates, description and payee, linked to the Imported transaction, with its Account Posting lookup row (Account transaction list). The Account Decider books only in the Open month and refuses again otherwise: a Close that ran meanwhile is caught by the Account's version check | Category totals, Budget actuals, Forecasts, Match suggestions |
| Accept as Transfer | Ingestion → Ledger | `category_id` with `transfer_account_id` refused first (`invalid-transfer`, `CATEGORY_AND_TRANSFER`), and `match_transaction_id` without `transfer_account_id` (`MATCH_WITHOUT_TRANSFER`); then Ingestion's Accept checks as for Accept imported transaction (the row's month against its Account's Open month, then its own state), and the row marked Accepted and linked to the bank leg; through the Ledger port (`BookTransfer`): the cash Account checked (the row's own Account: `SAME_ACCOUNT`; not the Household's: `UNKNOWN_ACCOUNT`; not cash: `COUNTERPART_NOT_CASH`; another currency: `CURRENCY_MISMATCH`, all `invalid-transfer`); the bank leg (the row's amount, dates, description and payee, linked to the row, Account ↔ Account transfer, naming the cash Account) and the cash leg (the opposite amount, on the row's Transaction date as Booking and Transaction date, the row's description and payee, created by the Transfer, naming the row's Account) each booked by their Account Decider and recorded with their Account Posting lookup rows, in Account ID order so two Transfers can't deadlock; a cash leg in a closed month of the cash Account refused (`month-closed`, naming it in `account_id`; a later month is fine); with `match_transaction_id`, no cash leg is recorded: the given leg read and checked to be an In transit leg on the cash Account naming the row's Account with the opposite amount (otherwise `NOT_A_MATCHING_LEG`; no date window), and only the bank leg booked; the Match confirmed with the caller as `confirmed_by`, and both legs marked Matched, each by its own version check, so two Accepts racing for one manual leg let only one through | — |
| List transfer suggestions | Ingestion → Ledger | The Imported transaction read (404 outside the Household); through a Ledger port query, the cash Account checked as for Accept as Transfer (`invalid-transfer`), then its In transit legs naming the row's Account, with the opposite amount, within 7 days either side of the row's Transaction date, read from the Account Posting lookup rows, closest first. Nothing is stored | — |
| Set Transaction Category | Ledger | Transaction's Category on the non-Account side changed with Accept's Category rules (Uncategorised allowed, any other Internal Category refused), its amount untouched; refused for a reversed Transaction, a reversal and the Opening balance Transaction, and for a Transfer leg (`transfer-leg`, checked before the Category is read); Account's Uncategorised count for the Booking month moved in or out; its Account Posting lookup row updated (Account transaction list). The same Category again records nothing. In a closed month (before the Account's Open month) any other Category can be chosen, but moving to Uncategorised is refused by the Account Decider (`uncategorised-in-closed-month`), since the close checked that nothing there was Uncategorised (ADR-0024) | Category totals, Budget actuals |
| Reverse Transaction | Ledger → Ingestion | Transaction marked reversed (refused for the Opening balance Transaction, a reversal, or one already reversed); reversing Transaction recorded with the opposite Postings, the same dates, description and payee, linked both ways; every touched Account's balance moved back in the Booking month and the original taken out of its Uncategorised count (neither counts); both Account Posting lookup rows in the Account transaction list; through the Ingestion port, the linked Imported transaction back to pending and unlinked, so it can be Accepted again or Discarded. A Transaction booked in a closed month (before the Account's Open month) can't be reversed: the Account Decider refuses (`month-closed`), after the Transaction's own refusals (ADR-0024) | Category totals, Budget actuals |
| Reverse Transaction (Transfer leg) | Ledger → Ingestion | As Reverse Transaction, plus, for a Matched leg: the Match removed (`match.removed`) and both legs unmatched, each by its own version check; the other leg reversed too when it is the cash leg an Accept as Transfer recorded on its own, or when both legs are on cash Accounts (cash ↔ cash: reversing either reverses both) (a manual cash leg stays, In transit, and so does a bank leg whose automatic cash leg is reversed alone; the Domain refuses reversing a leg still Matched); every reversal booked on its Account in Account ID order, and the bank leg's Imported transaction returned to pending through Ingestion. A closed month of any Account it would book on refuses the whole command (`month-closed`, naming that Account in `account_id`), and the database transaction leaves nothing recorded. A reversal never names a counterpart, so it is never In transit | — |
| Close month | Ledger ← Ingestion | Account read (refused while awaiting its first Statement import, for a month before its start date, or for a Statement balance in another currency or with too many decimal places); through the Ingestion port the Account's Statement imports locked, then its pending and Suspected duplicate Imported transactions booked in the month counted and its non-voided Statement imports with rows in or before the month whose Balance check is waiting or failed listed; the Account Decider closes only the Account's Open month (ADR-0024): a month after it is refused as not open yet and a month before it as already closed, both naming the Open month, and the Open month itself is refused until it has ended (from the first day of the next month, by the server's clock in UTC); otherwise it checks every condition (none pending, no undecided Suspected duplicate, nothing in Uncategorised, no waiting or failed check, computed closing balance (Opening balance plus every month up to this one) equal to the Statement balance) and refuses with every failed one together; Account month marked closed with its Statement balance, when and by whom, and the month after it (December rolling into January) becomes the Account's Open month, so months close one at a time, in order. Nothing is booked: there is no balancing entry (ADR-0018) | — |
| Reopen month | Ledger | Account read (refused as not found outside the Household); the Account Decider takes back only the Account's latest Month close (the month just before its Open month) while the Open month has no Accepted Transactions that aren't reversed, and otherwise refuses with every failed condition together (`month-reopen-refused`: the month isn't closed, it isn't the latest closed month, or the Open month's Accepted count, so they are reversed first); the month's Statement balance and close are dropped, it becomes the Account's Open month again and the month after it is not open yet, so it must be closed again with its Statement balance (ADR-0024). Writing the Account's fold row serialises it against a Keep or Discard on the Account, which holds that row `FOR SHARE`, and an Accept that raced it is refused by the Account's version check. Nothing is booked, and Imported transactions keep their states: pending rows of the month after it wait again | — |
| Close month (cash) | Ledger | As Close month, except: `counted_on` required for a cash Account and refused for any other (400 `invalid-month-closing`), checked before the Account's other states; a `counted_on` on or before the month's last day, or after today in UTC, refused (`invalid-count-date`); the Account's fold row locked `FOR UPDATE`, then its Account Posting lookup rows booked after the month's last day up to and including `counted_on` summed, so a cash Transaction booked concurrently in that window either is summed or waits and fails its version check; the Account Decider compares the count with the balance at the end of `counted_on` (the month's closing balance plus that sum), and a gap is the `month-close-refused` balance mismatch; the month-end balance the count proves is stored as the Statement balance, with the count and `counted_on`. The Ingestion conditions are read as for any Account and are empty for cash | — |
| Reopen month (cash) | Ledger | As Reopen month, without the Open month's Accepted-Transactions condition: the later months' cash Transactions stay, and the Cash count is dropped with the close, so the month closes again with a new count | — |
| Mark Notification read | Households | Notification marked read for the caller only (refused as not found for another Household's or an unknown one); marking it read again records nothing | — |
| Rename or move Category | Ledger | Household's Category tree locked; new parent and sibling names read and checked; Category renamed and/or moved | — |
